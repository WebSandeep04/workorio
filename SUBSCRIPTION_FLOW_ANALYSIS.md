# Subscription Module Flow Analysis

This document provides a detailed analysis of the Subscription Module flow, accessible at `/subscriptions`. It covers the user interface, backend logic, database schema, and specific workflows for creating and managing subscriptions.

## 1. Overview

The Subscription Module is designed to manage recurring and one-time billing for customers. It allows users to:
- View a dashboard of subscription statistics.
- Filter and search for specific subscriptions.
- Create new subscriptions with flexible recurrence patterns (Daily, Weekly, Monthly, etc.).
- Track the history of billing cycles.
- Automatically generate future billing cycles upon consistency of payment.

## 2. Component Architecture

### Backend (Laravel)
- **Controller**: `App\Http\Controllers\SubscriptionController`
- **Models**: `App\Models\Subscription`, `App\Models\Customer`, `App\Models\SalesProduct`
- **Database Tables**:
    - `subscriptions`: Stores the core configuration (amount, recurrence rules, current status).
    - `subscription_histories`: Stores individual billing cycles (past and future-due).

### Frontend (Blade & jQuery)
- **View**: `resources/views/subscription/index.blade.php`
- **Modals**: Add, Edit, View Details.
- **Logic**: AJAX-based data loading, filtering, and form submission.

## 3. Database Schema

### `subscriptions` Table
Stores the master record for a subscription.
- **Core Links**: `customer_id`, `product_id`, `user_id` (owner).
- **Financials**: `amount`, `billing_type` (Prepaid/Postpaid).
- **Recurrence**: 
    - `is_recurring` (Boolean)
    - `recurrence_type` (daily, weekly, monthly, quarterly, half_yearly, yearly)
    - `recurrence_interval` (e.g., "Every 2 weeks")
    - `recurrence_days_of_week` (JSON, e.g., `["mon", "fri"]`)
    - `recurrence_day_of_month` (1-31)
- **Status**: `status` (Current status), `is_active` (Boolean switch).
- **Dates**: `start_date`, `next_billing_date`, `last_billed_date`.

### `subscription_histories` Table
Tracks the individual billing periods generated by the subscription logic.
- **Dates**: 
    - `period_start`: Start of the billing cycle.
    - `period_end`: End of the billing cycle.
    - `due_date`: Payment due date (varies by Prepaid/Postpaid).
- **Status**: Status of this specific cycle (e.g., "Pending", "Payment Received").
- **Amount**: Snapshot of the amount for this cycle.

## 4. Comprehensive Workflow Analysis

### 4.1. Page Initialization & Listing Flow

When a user visits `http://localhost:8000/subscriptions`:

1.  **View Rendering**: The `index()` method returns the `subscription.index` view.
    - **Summary Stats**: It pre-calculates and passes:
        - `totalCustomers`: Count of customers with active subscriptions.
        - `totalSubscriptions`: Total count of subscription records.
        - `comingDueCount`: Subscriptions/Histories due in the next 15 days.
        - `overDueCount`: Histories past their due date.

2.  **Dropdown Population (AJAX)**:
    - On page load, the frontend fires parallel AJAX requests to fetch "Master Data" for dropdowns:
        - `subscription-status.list`: Populates Status filters.
        - `subscriptions.customers`: Populates Customer dropdowns.
        - `subscriptions.products`: Populates Product dropdowns.

3.  **Data Loading (AJAX)**:
    - The `loadData()` JS function is called. It reads all active filters (Customer, Product, Status, Recurrence, Active).
    - **Route**: It targets `route('subscriptions.filter')` (mapped to `SubscriptionController@filterSubscriptions`).
    - **Pagination**: The server returns a JSON paginated response.
    - **Rendering**: Result rows are dynamically appended to the `#data_table` body.

### 4.2. Creation Flow (Add Subscription)

Step-by-step logic when a user creates a subscription:

1.  **User Action**: Clicks "Add Subscription" -> Fills Modal Form -> Clicks "Save".
2.  **Frontend**:
    - Validates inputs.
    - Constructs `FormData` including complex recurrence arrays (e.g., `recurrence_days_of_week[]`).
    - POSTs to `/subscriptions`.
3.  **Backend (`store` method)**:
    - **Validation**: Ensures required fields (Amount, Start Date, Status) and conditional fields (Recurrence Type if Recurring) are present.
    - **DB Insertion**: Creates a record in the `subscriptions` table.
    - **Customer Update**: Sets the linked Customer's `is_subscription_on` flag to `1`.
    - **History Generation (The Loop)**:
        - The system calculates the first billing cycle starting at `start_date`.
        - **Backdating Logic**: It enters a `do-while` loop.
        - If `start_date` is in the past, it generates *multiple* history records (cycles) until it catches up to the current date (`Carbon::now()`).
        - If `start_date` is in the future, it generates only the initial cycle.
        - **Prepaid vs Postpaid**: 
            - **Prepaid**: `due_date` = Cycle Start Date.
            - **Postpaid**: `due_date` = Cycle End Date.

### 4.3. Status Update & Cycle Continuation

This is the most critical logic for recurring subscriptions.

1.  **Trigger**: User updates a subscription's status to **"Payment Received"** (via Edit or Status Dropdown).
2.  **Backend (`updateStatus` method)**:
    - Updates the `subscriptions` table status.
    - Updates the *latest* `subscription_histories` record status.
3.  **Next Cycle Generation**:
    - The system checks: Is Status == "Payment Received" AND Is Active == True AND Is Recurring == True?
    - If **YES**:
        1.  **Calculate Next Start**: `nextStartDate` = Current Cycle End Date + 1 Day.
        2.  **Calculate Next End**: Adds the recurrence interval (e.g., +1 Month) to the new start date.
        3.  **Calculate Next Due**: Determines due date based on Billing Type.
        4.  **Insert**: Creates a NEW `subscription_histories` record with status **"Pending"**.
    - **Result**: The system essentially "extends" the subscription by one cycle automatically upon payment.

### 4.4. Filtering Logic

The filtering system uses the `filterSubscriptions` method:
- **Scope**: Optionally filters by `user_id` (User's own subscriptions).
- **Criteria**:
    - `customer_id`, `product_id`, `status`: Direct matches.
    - `search`: Performs a `LIKE` query on `notes` OR `customer.name` OR `customer.email`.
    - `is_recurring`: Boolean filter.
    - `recurrence_type`: Enum match (e.g., 'monthly').

### 4.5. Editing Logic

- **Endpoint**: `PUT /subscriptions/{id}` (`update` method).
- **Behavior**:
    - Updates core subscription details (Amount, Recurrence Config).
    - **Does NOT** automatically regenerate history. History modifications must handle the specific `subscription_histories` records directly (though the UI primarily exposes editing the *current* master record).

### 4.6. Automated Recurring Billing (Cron Job)

To ensure billing cycles are generated even if the previous payment is pending (accumulating dues):

1.  **Command**: `php artisan subscriptions:generate-recurring`
    - Should be scheduled to run daily (e.g., at midnight).
2.  **Logic**:
    - Iterates through **All Tenants**.
    - Finds active, recurring subscriptions.
    - Checks the **Latest History Record**.
    - If the latest cycle has ended (e.g., Ended Jan 31 and Today is Feb 1), it **automatically generates the next cycle** (Feb 1 - Feb 28).
    - The new cycle status is set to **"Pending"**.
3.  **Outcome**:
    - Allows for "accumulating" invoices/dues.
    - A customer can have multiple "Pending" history records (e.g., Jan Pending, Feb Pending).

## 5. Key Business Rules


1.  **Recurrence Types**:
    - **Daily/Weekly/Monthly/Quarterly/Half-Yearly/Yearly**.
    - Specialized logic handles "Day of Month" (e.g., bill on the 5th) and "Days of Week" (e.g., every Mon/Fri).

2.  **Inactivity**:
    - Setting `is_active = false` stops the automated generation of future cycles, even if "Payment Received" is marked.

3.  **Deleting**:
    - Deleting a subscription (`destroy`) performs a hard delete, cascading to remove all associated `subscription_histories`.
